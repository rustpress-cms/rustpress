# Plan: RustPress, a drop-in replacement for WordPress without PHP

## Context

Goal: existing WordPress sites run without PHP and without converting the database. The Rust binary reads the existing MySQL/MariaDB (the original `wp_*` schema) and the existing `wp-content/` directly.

Decided (agreed with the maintainer):
- **Themes/plugins:** only block themes are supported (`theme.json` + HTML templates, no PHP needed). Important plugins are rebuilt later as native Rust modules. Classic PHP themes and arbitrary PHP plugins deliberately do not run.
- **Milestone 1:** read-only front end (pages, posts, archives, feeds, REST API for reading). There is no write access to the database.
- **Database:** MySQL/MariaDB through `sqlx`.

State at the start: a workspace with one crate, `crates/rustpress-phpser` (`unserialize`/`serialize` in `src/lib.rs`, 8 tests green). The toolchain `stable-x86_64-pc-windows-msvc` is set up. PHP and MySQL are not installed locally.

## Target architecture (workspace crates)

| Crate | Purpose |
|---|---|
| `rustpress-phpser` (exists) | PHP serialize, byte-exact. Gets references (`R:`/`r:`) and `S:`. |
| `rustpress-db` | `sqlx` MySQL pool, table prefix from the config, typed reads for `posts`, `postmeta`, `options`, `terms`, `term_taxonomy`, `term_relationships`, `users`, `usermeta`, `comments`. The connection is only used for reading. |
| `rustpress-core` | Options cache (uses `phpser` for serialized values), post query (a subset of `WP_Query`), permalink/rewrite resolution from `permalink_structure` and `rewrite_rules`, template hierarchy. |
| `rustpress-blocks` | Parser for block comments (`<!-- wp:name {json} -->`) and renderer for the core blocks, first paragraph, heading, image, list, group, columns, post-title, post-content, query, navigation, template-part. |
| `rustpress-theme` | `theme.json`, `templates/*.html`, `parts/*.html`, global styles CSS generator, resolving the active theme from the options `template`/`stylesheet`. |
| `rustpress-server` | `axum` binary: routing, static files (`wp-content/uploads`, theme assets), configuration (database URL, WordPress path), logging. |
| `rustpress-compat` (tests only) | Golden tests: the same URL against a real WordPress and against RustPress, the normalized HTML is compared. |

- Byte-exact HTML equality is unrealistic, because WordPress filters (`wptexturize`, `wpautop`, emoji scripts) change a lot. So the comparison happens after normalization, and the filters are rebuilt one by one.

## Localization

Goal: hundreds of languages without writing code for any one of them. The concept is implemented and compared with the real WordPress in four languages.

**Principles**

1. **WordPress's language packs are the only source.** RustPress loads `wp-content/languages/<locale>.mo` (domain `default`) and, per theme, `wp-content/languages/themes/<slug>-<locale>.mo` (fallback: the theme's `languages/<locale>.mo`). The site language is the option `WPLANG`. A new language is a new `.mo` file; translate.wordpress.org provides about 200 of them.
2. **The code contains only the English message IDs, exactly like WordPress.** Access goes only through `Site::tr` / `trx` (context) / `trn` (plural) and `rustpress_core::i18n::sprintf` (`%s`, `%1$s`, `%d`). Theme and pattern texts go through `PhpHost::translate(text, context, domain)` with the theme's text domain. REST errors carry their message ID and arguments (`Msg`) and are translated only when serialized, so endpoint code never sees a language.
3. **`LocaleData` is `WP_Locale`** (`rustpress-core/src/locale.rs`): weekdays and months with abbreviations, genitive months, meridiem, thousands and decimal separators, list separators, text direction, `html_lang_attribute`, word count type, "decline months". It is built once per catalog, not per call.
4. **Language-dependent algorithms depend only on catalog values:** `wp_date` with `wp_maybe_decline_date` (Russian, Polish, Finnish …), `wptexturize` with the language's quotes, apostrophes, dashes and Cockney list (`TexturizeChars`), `wp_trim_words` by characters instead of words (Chinese, Japanese, Korean), plural rules as any GNU gettext expression (`Plural-Forms`, up to 6 forms), `excerpt_length`, right to left (`dir="rtl"`, the body class `rtl`, `-rtl` stylesheets for blocks and `wp-block-library`, sitemap XSL).
5. **Texts that WordPress translates with placeholders stay templates** (`"%1$s Avatar"`, `"%s submenu"`, `"Comment on %1$s by %2$s"`), never sentences put together; lists ("a, b and c") use the language's separators (`wp_sprintf_l`).

**Safeguards**

- `crates/rustpress-core/tests/i18n_coverage.rs` reads the source of all crates and checks that every message ID from `tr`/`trx`/`trn`/`RestError`/`Msg` exists in WordPress's German core pack. That catches typos and changed English texts that no language pack could translate any more (it has already found two REST error messages that WordPress does not know at all). Without a language pack it skips itself.
- `dev/compat.ps1 -Locale <locale>` switches the reference WordPress to the language (core and theme packs are installed, afterwards it goes back to `en_US`) and compares the whole compat run. The four languages cover the structure of the others: **de_DE** (quotes „ “, date and list formats, texts), **ru_RU** (three plural forms, genitive months, Cyrillic characters), **ar** (right to left, six plural forms, Arabic script) and **ja** (word count by characters, `※` as the required field mark, CJK script).
- **Result** (reference WordPress 7.1.3 in each language, all three bundled block themes, 167 to 171 URLs per run): de_DE, ru_RU, ar and ja give **0 unexpected differences in all twelve runs** with Twenty Twenty-Five, -Four and -Three (154 to 156 URLs identical, the rest are the known differences from `compat/known.toml`). The English regression stays at 0. Reports: `compat/reports/<theme>-<locale>.md`.
- Bugs found: `esc_html()` cut a multibyte character in the middle after `&` (a panic with Cyrillic text); the comment form, password form, pagination, search block, feed titles, sitemap XSL and many other places had fixed English texts; the REST errors for `orderby=include` on terms did not exist in WordPress.

**Operation**

- RustPress writes no language packs. They are installed as for WordPress (WP-CLI `language core install`, a ZIP from translate.wordpress.org). Planned: `rustpress i18n install <locale>` as an explicit command that downloads the packs from `api.wordpress.org/translations`.
- A core catalog is about 0.5 MB; only the site language is loaded, and the names and characters of the language (`LocaleData`, `Texturize`) are built once on first use.

**Open**

- A language per request (the user's language, multilingual plugins such as Polylang or WPML): `Site` holds exactly one language today. Planned is an `I18nRegistry` (locale -> `Arc<I18n>`, loaded lazily) from which `Env` gets a `Translator` per request; all calls already go through `Site::tr`, so only that one place moves.
- JavaScript translations (`<handle>-<locale>-<hash>.json`, `wp_set_script_translations`) for Interactivity texts.
- Hot reload of language packs (today: on restart or theme reload) and variants such as `de_DE_formal` (WordPress loads a separate complete pack for it, so no fallback is needed).
- Twenty Twenty-Seven does not exist on wordpress.org (yet); block themes from other sources run as soon as their files are under `wp-content/themes/`.

**Custom post types and taxonomies** (`rustpress-core/src/types.rs`, `php_lit.rs`): WordPress knows them from PHP (`register_post_type()`), and RustPress runs no PHP. So they are recognized in two stages:
1. From the stored rewrite rules (`rewrite_rules`) for the types and taxonomies that occur in `wp_posts`/`wp_term_taxonomy`: slug, archive (also `has_archive => 'kalender'`), hierarchical (`(.+?)`), taxonomy slug. A type without rules (plain permalinks) stays invisible.
2. From the source of the active plugins, the must-use plugins and the theme, as far as the arguments are literals (`php_lit.rs` reads strings, numbers, arrays, `__()`, concatenation and variables that were assigned an array before): `label`/`labels`, `public`, `publicly_queryable`, `exclude_from_search`, `supports`, `show_in_rest`, `rest_base`, `hierarchical`, `menu_icon`, `description`. Non-public types disappear from the front end, sitemaps and search that way.
With that, single pages (also hierarchical), archives, taxonomy pages, `?post_type=`/`?book=`/`?genre=`, the template hierarchy (`single-book`, `archive-book`, `taxonomy-genre`), body/post classes, permalinks, sitemaps, feeds, search, `?p=ID` (WordPress treats other types as a 404 and canonicalizes; that brings the no-cache headers), the feed links in the head and the REST routes (`wp/v2/<rest_base>`, terms, `types`, `taxonomies`) work. Limits: literals only (computed arguments stay at their defaults), labels are not translated (the plugin's text domain is not loaded), `core/query-title` of type `post-type` is missing.

**Embeds and oEmbed** (`rustpress-theme/src/embed.rs`, `rustpress-rest/src/oembed.rs`): the embed page `/post/embed/` (`theme-compat/embed*.php`: title, excerpt, featured image, the comment and share buttons with the dialog, inline scripts, `X-WP-embed`), the HTML to embed (`get_post_embed_html()`, a random secret) and the provider `wp-json/oembed/1.0/embed` (JSON and XML, errors as XML, width limits, `url_to_postid()`); `proxy` is for editors only, as in WordPress. Random values (the secret, ID counters) are neutralized in the comparison.

**More core blocks with server-side changes** (`rustpress-blocks/src/dynamic/`, seeds `dev/seed_blocks2.sh`, `seed_blocks3.sh`; pages `/mehr-bloecke/`, `/video-und-co/`, `/akkordeon/`): `core/button` (empty buttons are dropped, width and width presets), `core/cover` and `core/media-text` with the featured image, `core/details` (images with `fetchpriority=low`), `core/footnotes` with `excerpt_remove_footnotes()`, `core/breadcrumbs`, `core/video` (dimensions and `aspect-ratio` from the metadata), `core/accordion` and `-item`. Plus an **Interactivity processor** (`interactivity.rs`, a port of `WP_Interactivity_API::process_directives()`): `data-wp-interactive`, `-context`, `-bind`, `-class`, `-style`, `-text` are evaluated once per "root block" as in WordPress; state (`wp_interactivity_state`) and derived state end up in the script `wp-script-module-data-@wordpress/interactivity`. Script modules are listed in the order they were requested. Open: `core/tabs`, `core/icon`, `core/playlist`, `core/rss` (network), lightbox, `data-wp-each`.

**Quirks that WordPress has and RustPress reproduces** (each found with the oracle): page number links carry the query arguments of the request (`urlencode_deep`); `?p=ID` of another type is a 404 that `redirect_canonical()` corrects with no-cache headers; the matches of a rewrite rule go through `urlencode` and `parse_str` (`%2D` stays `%2D`); only public query variables from permalinks; on a port other than 80/443 WordPress never redirects paging and feed addresses because of its protection against chained redirects (`canonical_redirect_for_request`); feeds are sorted by date, also for searches; a feed of a missing page or category is an empty feed (200); `get_avatar()` counts the image even when `show_avatars` is off.

**REST** (`rustpress-rest`): `posts`, `pages`, `media`, `categories`, `tags`, `users`, `comments` and new `types`, `taxonomies`, `statuses`, `search`, `blocks`, `navigation`, the routes of custom types and taxonomies, and the 401 answers of the administration routes (`settings`, `themes`, `plugins`, `widgets`, `menus`, `templates`, `block-types`, …) with WordPress's codes and texts. ## Administration (wp-admin): plan (decision of 2026-10-25)

The front-end comparison is largely exhausted (remaining list above). The next big block is the administration, which is what makes WordPress for editors and administrators. For the first time it needs **write access** to the database. Decided (without asking back, since "carry on with the admin side" was requested):

1. **Writing is an explicit switch.** The existing pool stays `READ ONLY`. The administration gets a second connection (`allow_writes = true` in the configuration, otherwise never opened). Without the switch RustPress stays a pure read replacement, and `wp-login.php`/`wp-admin` answer as before.
2. **The real block editor, not a rebuild.** WordPress ships the editor as JavaScript (`wp-includes/js/dist/*.js`, `wp-includes/css/dist/**`); it talks only to the REST API. RustPress delivers the HTML shell (`post.php`, `post-new.php`: the script loader with the dependencies from the `*.asset.php` files, preloaded REST answers, the editor settings) and the write API. That is much less work than an editor of its own and looks like WordPress.
3. **Order**, each compared with the oracle (the reference WordPress) as far as the oracle shows it:
   - **A. Session and permissions**: password check (`$P$` phpass, `$wp$2y$` and bcrypt), the cookies `wordpress_logged_in_*`/`wordpress_sec_*` with `wp_hash()`, sessions in `usermeta` (`session_tokens`), roles and capabilities (`wp_user_roles`, `capabilities` per user), nonces; `wp-login.php` (sign in, sign out, error messages, "remember me"); keys and salts from `wp-config.php` if there is one, otherwise its own (existing sessions then expire).
   - **B. The front end for signed-in users**: admin bar, private and draft posts with preview, password cookies, a prefilled comment form, "Edit" links, `core/comment-edit-link`, `current_user_can()` in all blocks.
   - **C. REST with sign-in**: cookie plus `X-WP-Nonce`, application passwords, then the write endpoints (`posts`, `pages`, `media` with upload, `categories`/`tags`, `comments`, `users`, `settings`), revisions, autosaves, locks.
   - **D. wp-admin itself**: dashboard, post lists (`edit.php`), editor (`post.php`), media (`upload.php`), comments, users, settings, themes (the site editor is JavaScript over REST too), plugins (display only; without PHP no plugin pages run).
   - **E. Posting comments** (`wp-comments-post.php`), password pages, search in the administration.
4. **Not planned**: running PHP plugins, Multisite administration, updates from wordpress.org (an explicit command later).

## B. Structural improvements (ordered by value)

1. **`map_meta_cap` in one place** in `rustpress-auth::CurrentUser` (`can_edit_post`, `can_delete_post`, `can_read_post`, `can_edit_comment`, `can_edit_user`) – model `rustpress-rest/src/edit/caps.rs`. Closes S1–S4, S6–S8, R12, R15 at once.
2. **`Allowed::post()`** in `rustpress-core::kses` + applied to all HTML output fed from attributes (S5). At the same time replace `core/plugins.rs::kses_data` with `kses::kses`.
3. **A robustness budget**: a depth limit in the renderer, visited sets for parent chains, `saturating_*` for page numbers, a depth limit in the deserializer, `.get()` instead of indexing. Principle: *no panic from user data* – Clippy `unwrap_used`/`indexing_slicing` as `warn` for the crates blocks/rest/admin.
4. **Don't swallow errors**: Clippy `let_underscore_future` = `deny` (finds R1), `let_underscore_must_use`; write paths return a `Result`, the screens show the WP error page.
5. **A per-request cache in `State`** (blocks/env.rs): comments, users, posts, terms, query block results; **a process cache at `Theme::load`**: static WP files, the global stylesheet, template lists, the icon manifest. Regexes in `LazyLock` everywhere.
6. **Batch helpers in `rustpress-db`** (`post_meta_many`, `terms_for_posts`, use `users_by_ids`, `revision_count_and_latest`, count queries) and LIMIT/search in SQL instead of in Rust.
7. **`spawn_blocking`** around image, ZIP and directory work.
8. **Shared helpers** (`validate_redirect`, `origin`, `esc_textarea`, `sticky_ids`, `sanitize_key`, LIKE escaping, one comment form function).
9. **Tests**: (a) a database suite with a seeded schema (`sqlx::test`), (b) a role matrix per admin/Ajax/REST action (subscriber/contributor/author/editor/admin → the expected WP answer, no write access), (c) hostile inputs (attributes, cycles, depth, overflow), (d) golden tests in CI with the reference, or `#[ignore]` instead of silently skipping.
10. **Lint configuration** in the workspace (`[workspace.lints.clippy]`) for the rules above; `cargo clippy` in the dev scripts.
